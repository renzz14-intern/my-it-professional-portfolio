STEP 18 / DEFENSIVE CASE STUDY

Cybersecurity case

SQL injection vulnerability
General learning scenario

This is a general defensive example, not a finding about Serenity Spa. No vulnerability assessment of that application is claimed.

01

What is the vulnerability?

SQL injection occurs when an application treats untrusted input as part of a SQL command instead of as data. A database query can then behave differently from the developer's intended operation.

02

How can it happen?

It can happen when code builds a query by joining user input into a SQL string, such as for a login, search, or filter. If the input is not bound as a parameter, the database may interpret it as query syntax. Dynamic table or sort names also need strict allow-lists.

03

What are the risks?

Depending on database permissions and the affected query, an attacker might read, alter, or delete data, bypass parts of an application's intended access flow, or disrupt service. Exposure of personal or health information can create serious privacy harm.

04

How can developers prevent it?

Use prepared statements with bound parameters for values; never assemble SQL by concatenating user input. Use an ORM safely where appropriate, allow-list dynamic identifiers, grant the database account only the permissions it needs, and return generic errors to users.

05

What practices should be implemented?

Include secure-code review, parameterized-query checks, dependency updates, least privilege, protected secrets, safe error handling, monitoring, and tested backups. Run authorized security tests in a controlled staging environment with dummy data, then fix and retest findings.

RESPONSIBLE PRACTICE

Test only systems you own or have explicit permission to assess. Do not use real customer data or publish credentials, sensitive records, or unverified vulnerability claims.
